## Findings considered and rejected

- **REST `/api/clients` not scoped by employee**: not worth doing because the PRD states associates can "view all clients (read-only for others)." The API matches the intended design.
- **`lib/queries.ts` god object (947 lines)**: not worth a plan now because the file is well-organized (49 focused exports, zero dead code) and splitting it would be churn without clear payoff at this repo's size.
- **4 action modules bypass the barrel**: not worth doing because the direct imports are deliberate (model-catalog is imported by 5 files; the barrel is a convenience for UI components, not a hard architectural boundary).
- **date-fns duplication (3.6.0 + 4.3.0)**: not worth doing because 4.3.0 is a transitive dep of react-day-picker; deduping would require pinning react-day-picker's date-fns version, which risks compatibility issues. Both versions are small and tree-shake independently.
- **better-sqlite3 11→12**: the drizzle upgrade (004) landed without requiring this. No incompatibility was reported. Not worth a standalone plan.
- **No pre-commit hooks / prettier / editorconfig**: not worth doing now — single-developer repo, trunk-based, no remote. These are CI/team-scaling tools that add friction without payoff at this stage.
- **27 console.error in production**: not worth doing — all are legitimate catch-path error logging, not debug leftovers. Structured logging (pino/winston) is overkill for a single-tenant kiosk.
- **next-auth 4.x → 5.x (Auth.js) migration**: not worth doing now. next-auth 4.24.14 works with Next.js 15 and has no critical advisories. The v5 migration is a significant breaking change (new API surface, session handling) with no security driver at this time.
- **uuid < 11.1.1 advisory (via next-auth)**: not worth doing. next-auth uses uuid v4 (random UUID generation), and the advisory (GHSA-w5hq-g745-h8pq) affects v3/v5/v6 buffer-based generation only. The vulnerable code path is not reachable.
- **Plan 008 (createPromo redundant catalog scan)**: likely a no-op. The plan's Step 1 verifies whether the redundancy exists and will self-reject if not. Listed as P3/TODO so the executor confirms it.

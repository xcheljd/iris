## Execution notes (2026-08-10)

- **013 DEFERRED — the plan's proposed fix breaks duplicate detection.** It replaces the
  in-memory match with `eq(clients.email, email)` / `eq(clients.phone, phone)`, but
  `clients.email` and `clients.phone` are plain `text()` with no `COLLATE NOCASE`, and
  phone is stored raw (`(555) 123-4567`) while `normalizePhone` strips to digits
  (`5551234567`). The current code normalizes *both* sides; the SQL version only
  normalizes the input, so graduation would stop matching existing clients and start
  creating duplicates. Needs an expression index or a SQL-side normalization before it
  can proceed. The full scan itself is not a live problem at this repo's size.
- **011 BLOCKED — the guard as specified is over-broad and breaks an existing test.**
  `lib/queries.ts:435,702` scope smart-list visibility to `ownerId = you OR isShared`,
  so shared lists are deliberately visible to everyone; the plan's guard would block
  duplicating them. It also breaks the passing test "copy is owned by the duplicating
  user, not the original owner", which creates a *private* manager list and duplicates
  it as an associate. Resolving this needs a product decision on smart-list sharing
  semantics: likely `!isManager && !isOwner && !isShared`, plus retargeting that test to
  a shared list.
- **Plan 012's proposed fix contained a latent bug** that was corrected during execution:
  building the `alreadyUnsubbed` Set once before the loop breaks when two clients share
  an email, because `unsubscribe_list.email` is UNIQUE while `clients.email` is not. The
  Set must be extended as rows are inserted. The same correction was applied to plan 014's
  in-plan fix for `bulkUnsubscribeProspects`.

## Findings considered and rejected (audit round 2 — 2026-06-24)

- **REST `/api/clients` and `/api/clients/[id]` not scoped by employee for associates (TC-02/03)**: BY DESIGN per plans/README.md (round 1): "associates can view all clients (read-only for others)." Subagent over-reported this as a finding; rejected after vetting against the PRD note already in this file.
- **`as string` casts in `lib/actions/clients.ts:300` preventing `||` fallback (TECH-01)**: Incorrect characterization. TypeScript `as` casts are compile-time only and have no runtime effect; the `||` operator evaluates the actual runtime value. Downgraded to a type-hygiene note; not worth a plan.
- **Missing explicit return in manager-only operations (CORRECTNESS-01)**: The affected functions return `undefined` implicitly, which is the correct return type. Not a bug.
- **Missing try-catch in manager-only operations (CORRECTNESS-02)**: The operations in question are reads inside manager flows with no concurrent mutation risk. Adding try-catch would be defensive noise; not worth a plan.
- **Dual COUNT + paginated data query in `lib/queries.ts:175-192` (PERF-04)**: Two SQLite round trips to count + paginate. At SQLite latency this is negligible (sub-millisecond). Not worth a plan.
- **REST API surface not exposed (DIRECTION-01)**: `docs/REST-API-EXPANSION.md` proposes 44 new endpoints. Accepted as a direction finding — informational, not a fix plan. Large effort; user decision required before planning.

## Findings considered and rejected (audit round 1)

- **REST `/api/clients` not scoped by employee**: not worth doing because the PRD states associates can "view all clients (read-only for others)." The API matches the intended design.
- **`lib/queries.ts` god object (947 lines)**: not worth a plan now because the file is well-organized (49 focused exports, zero dead code) and splitting it would be churn without clear payoff at this repo's size.
- **4 action modules bypass the barrel**: not worth doing because the direct imports are deliberate (model-catalog is imported by 5 files; the barrel is a convenience for UI components, not a hard architectural boundary).
- **date-fns duplication (3.6.0 + 4.3.0)**: not worth doing because 4.3.0 is a transitive dep of react-day-picker; deduping would require pinning react-day-picker's date-fns version, which risks compatibility issues. Both versions are small and tree-shake independently.
- **better-sqlite3 11→12**: the drizzle upgrade (004) landed without requiring this. No incompatibility was reported. Not worth a standalone plan.
- **No pre-commit hooks / prettier / editorconfig**: not worth doing now — single-developer repo, trunk-based, no remote. These are CI/team-scaling tools that add friction without payoff at this stage.
- **27 console.error in production**: not worth doing — all are legitimate catch-path error logging, not debug leftovers. Structured logging (pino/winston) is overkill for a single-tenant kiosk.
- **next-auth 4.x → 5.x (Auth.js) migration**: not worth doing now. next-auth 4.24.14 works with Next.js 15 and has no critical advisories. The v5 migration is a significant breaking change (new API surface, session handling) with no security driver at this time.
- **uuid < 11.1.1 advisory (via next-auth)**: not worth doing. next-auth uses uuid v4 (random UUID generation), and the advisory (GHSA-w5hq-g745-h8pq) affects v3/v5/v6 buffer-based generation only. The vulnerable code path is not reachable.
- **Plan 008 (createPromo redundant catalog scan)**: likely a no-op. The plan's Step 1 verifies whether the redundancy exists and will self-reject if not. Listed as P3/TODO so the executor confirms it.
